1. HOW WE WERE ABLE TO WRITE THE "PLUGINS" (integrations)
--------------------------------------------------------------------------
What the audience sees: each demo can inject a failure, investigate it, and
recover — as if we "rolled our own plugins" for OpenSRE. What really happens:

a) OpenSRE CLI as the AI core (not a custom model):
   - Binary:  /home/subrata/.local/bin/opensre (v0.1.2026.9.1+main.eee45fa)
   - Subcommands used: investigate, doctor, status, onboard.
   - CLI config: ~/.opensre/opensre.json  -> target "local", provider
     "gemini", default model gemini-3.1-flash-lite-preview.
   - Every analysis is issued as:
        opensre investigate --input-json '<alert|evidence JSON>'
     (backend helper: opensre-backend/app/services/opensre_cli.py)

b) The "plugin" is really two layers WE wrote in the backend:
   1) Integration service module (app/services/<system>.py) — a self-
      contained, READ-ONLY adapter that normalizes a system into bounded,
      structured evidence. Each exposes functions like:
        health(), <query>/log_analysis(), and a collector returning
        structured dicts (capped tails, never streaming the whole log).
      Examples:
        nginx.py         ingress health + `nginx -t`/`nginx -T` + log decode
        yugabyte.py      read-only SQL connector (only SELECT/WITH/SHOW/
                         EXPLAIN/DESCRIBE; mutation keywords rejected)
        aerospike.py     aerospike client, scans capped (MAX_SCAN_RECORDS)
        elasticsearch.py ELK pattern queries (ERROR/EXCEPTION/FAILED/
                         CONNECTION REFUSED/TIMEOUT)
        coredns.py       DNS health + live in-cluster resolution probe
        github.py        GitHub API (commits/branches/issues/workflows)
        grafana.py       Grafana health/datasources/dashboards
        victoriametrics.py  VM queries (rates, latency percentiles)
        kubectl.py       cluster / nodes / pods / services / deployments
   2) Orchestration (app/services/investigation.py) — collect_*_evidence()
      helpers bundle pod/node/coreDNS/nginx/ELK/db/VM/Grafana/git evidence,
      fold in a grounded `question`, and hand it to opensre_cli.investigate().
   The result (markdown RCA) is auto-saved via incident_history for the
   Incident Report page.

c) Demo scenarios are a THIRD layer (app/routes/*_demo.py) — each
   implements a deterministic fail -> investigate -> recover flow whose
   failure injection delegates to chaos/runbook.sh (real kubectl actions)
   and falls back to synthetic signals only when no cluster is reachable.

d) Inbound alerts (Grafana / Alertmanager / bare) are normalized into one
   object by _parse_alert_payload() in app/routes/opensre.py, then
   investigate() never forwards a bare alert: it collects evidence first
   and only then runs OpenSRE (grounded RCA, "Non-Validated Claims" avoided).

Pattern to mention in the talk: "adapter + bounded evidence + demo route +
opensre investigate --input-json". That is how the integrations were written.

2. GITHUB ISSUE CORRELATION
--------------------------------------------------------------------------
Implemented and demoable.
- Service:    app/services/github.py  (GitHubClient, REST via httpx)
              app/services/git_correlation.py
  Config:     GITHUB_TOKEN + GITHUB_REPO (7thGarden/AI_labtest) in
              opensre-backend/.env; default branch correlation.
- API routes: app/routes/github.py (prefix /api/github)
     GET /health        -> repo connection status
     GET /branches      -> branch list
     GET /commits?sha&since&until&limit
     GET /workflows     -> Actions runs
     GET /issues?state  -> open/closed issues
     GET /repo
     GET /workflow-runs/{id}/jobs        -> jobs + failed-step log snippets
     GET /workflow-runs/{id}/investigate -> evidence + OpenSRE RCA
- Correlation logic (git_correlation.py): given an incident start time,
  finds the newest commit at-or-before that time and marks it as the
  "suspected change-point", plus a window of commits before the incident.
  This is a read-only GitHub API lookup (never writes/pushes).
- Where it shows up: the GitHub page + every investigation demo degrades
  through the same collector — evidence digest lines like
  "suspected change-point commit ab12cd7 'message' (date)".
- Demo one-liner flow:
     1) Open GitHub page (frontend /github).
     2) Pick a workflow run, hit "Investigate" ->
        /api/github/workflow-runs/{id}/investigate.
     3) Or trigger any scenario below and point out the "git history"
        block in the RCA.
- Note: this is commit correlation and GitHub issues listing — not an
  outbound "open a GitHub issue" action.

3. NGINX INTEGRATION AND CONFIGURATION ISSUES
--------------------------------------------------------------------------
Implemented and demoable.
- Deployment: infra/k8s/nginx-deployment.yaml (+ nginx-service.yaml) in
  namespace opensre, image nginx:1.27-alpine, probes hit /healthz.
- ConfigMap:  infra/k8s/nginx-configmap.yaml — structured access log
  (log_format "main" with rt/uct/upstream_status/uaddr), plus two
  observability endpoints /nginx-health and /nginx-status; upstream is
  catalog-api.opensre.svc.cluster.local:8000. This is what lets the demo
  decode upstream timing/502/503/504 from logs.
- Service:    app/services/nginx.py
     health()                    pod phase/readiness + restart counts
     nginx_config_test()         runs `nginx -t` inside the pod
     nginx_config_dump()         runs `nginx -T` (effective config, capped)
     get_nginx_logs(), analyze_logs()  parse access/error logs; error
     patterns incl. connection_refused, upstream_timeout, dns_failures.
- API routes: app/routes/nginx.py (prefix /api/nginx)
     GET /health  GET /config/validate  GET /config/dump
     GET /logs    GET /logs/analysis    GET /evidence  GET /investigate
  Plus the closed-loop demo: app/routes/nginx_demo.py
     POST /api/demo/nginx/fail?mode=broken_upstream | broken_dns
     POST /api/demo/nginx/investigate
     POST /api/demo/nginx/recover
- Demo one-liner flow:
     1) Frontend Nginx page -> "Inject failure" (broken upstream = 502/504
        storm from catalog-api, or broken DNS = upstream hostname fails to
        resolve).
     2) Investigate -> /api/nginx/investigate collects nginx evidence +
        K8s/VM/GitHub correlation; RCA points at the broken upstream/DNS.
     3) Recover -> config restored, /api/nginx/health + logs show green.
  - Show /api/nginx/config/validate (nginx -t) while broken vs. after fix.

4. YUGABYTE ISSUES
--------------------------------------------------------------------------
Implemented and demoable.
- Connector:  app/services/yugabyte.py (psycopg2 against yugabytedb at
  :5433, DB "yugabyte"). Read-only guard: READ_ONLY_SQL_PREFIXES =
  SELECT/WITH/SHOW/EXPLAIN/DESCRIBE; FORBIDDEN_SQL_KEYWORDS on mutation
  verbs. Mutations only via execute_raw() used by the demo seeder.
  Exposed: health, cluster_health, connection_status, slow_queries,
  recent_errors, schema_info, record_inspection, data_integrity_checks,
  table_statistics, replication_status.
- K8s: StatefulSet "yugabytedb" in namespace databases; port-forward
  svc/yugabytedb 5433:5433.
- Demo scenarios (app/routes/demo.py /api/demo/**), each fail->investigate->
  recover, DB-bin inclusive:
     db-scenario/unavailable      scale StatefulSet -> 0 (connection refused)
     db-scenario/latency          create latency_test table w/ 100 rows +
                                  unindexed LIKE query (slow query signal)
     db-scenario/connection-pressure  concurrent-like queries / big writes
     db-scenario/data-integrity   integrity_test: duplicate emails, NULL/
                                  empty names, negative counts (CHECK), dup
                                  PKs; plus insert-empty/duplicates/invalid
     db-failure/{fail,investigate,recover}  the "stop the database" demo
- API routes: app/routes/db_investigation.py (prefix /api/databases):
     GET  /yugabyte/health
     GET  /yugabyte/evidence          (or via /investigate/target/yugabyte)
     POST /yugabyte/custom-query ...
- Frontend: Yugabyte page (/yugabyte) — schema browser, slow_queries,
  record inspection, integrity checks; run scenario + "Investigate with
  OpenSRE".
- Important recovery detail: scaling StatefulSet to 0 kills the DB
  port-forward, so recover() re-runs kubectl port-forward automatically
  (services/portforward.py) and waits on `kubectl rollout status --timeout=240s`
  (YugabyteDB cold start ~2-3 min). Note it for the audience.

9. ELK INTEGRATION (ERRORS, EXCEPTIONS, FAILED, CONNECTION REFUSED, TIMEOUTS)
--------------------------------------------------------------------------
Implemented and demoable.
- Pipeline:
     catalog-api (structured JSON logs, catalog-api/app/core/logging.py
       JsonFormatter emits timestamp/service/level/message/error/request_id)
          -> pod stdout -> Fluent Bit DaemonSet
       (observability/fluent-bit.yaml: tail input /var/log/containers/*.log,
       kubernetes filter, nest lift -> k8s_* fields)
          -> Elasticsearch (helm, 8.5.1, observability/es-values.yaml)
       index template logs-opensre-* with ILM policy logs-opensre-policy
       (observability/install.sh creates template + policy + Kibana index).
          -> Kibana (helm, NodePort 30001, port-forward 5601)
- Service:  app/services/elasticsearch.py — PATTERNS dict mapping
  ERROR / EXCEPTION / FAILED / CONNECTION REFUSED / TIMEOUT to the
  fluent-bit field names; queryable by namespace/pod/service.
  evidence via investigation.collect_elasticsearch_evidence() +
  routes/opensre.py GET /api/opensre/investigate/elk.
- Demo: app/routes/elk_demo.py (prefix /api/demo/elk): SYNTHETIC_LOGS for
  the three failure classes —
     error              mode call catalog-api /failure/error
     connection-refused mode catalog-api /failure/connection-refused
     timeout            mode catalog-api /failure/timed-out|slow
  fail -> (see it land in ES/Kibana) -> investigate -> recover.
  chaos/runbook.sh also has elk-error, elk-connection-refused, elk-timeout
  injections via the catalog-api failure API.
- Frontend: Logs page (/logs) queries Elasticsearch for the five patterns;
  K8S page "Log Analysis" surfaces per-pod signal summaries.
- Kibana walk-through: filter logs-opensre-* for "CONNECTION REFUSED" or
  "TIMED OUT", show the k8s_pod_name field, then Investigate.
